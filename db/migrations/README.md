# db/migrations

SQL migration files for the bp-index Postgres schema, applied in date order.

Each file is idempotent (`IF NOT EXISTS`) and additive — existing tables are not altered or dropped. Run on the `production` schema of the bp-index Railway database.

## Applying a migration

```sh
# from the repo root, with .env.db loaded
PGPASSWORD=$DB_PASSWORD psql -h $DB_HOST -p $DB_PORT -U $DB_USER -d $DB_NAME \
    -f db/migrations/<file>.sql

# or, with DATABASE_URL from .env
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -f db/migrations/<file>.sql
```

## GraphQL exposure

The public PostGraphile endpoint (`dev-graphql.bpindex.org`) has **no auth** and connects as the postgres superuser, so anything it exposes is world-writable. It turns every `VOLATILE` function in `production` into a mutation, so **every new write function must carry an `@omit` smart comment**. Admin actions go through the session-checked `pages/api/admin/*` routes over pg (`lib/admin/*`), never through GraphQL. When a function has a description, keep it below the tag:

```sql
COMMENT ON FUNCTION production.my_fn() IS E'@omit\nWhat it does.';
```

Re-running `2026_09_23_2_omit_graphql_mutations.sql` sweeps any unhidden ones. To check, this should return `"mutationType":null`:

```sh
curl -s https://dev-graphql.bpindex.org/graphql -H 'Content-Type: application/json' \
    -d '{"query":"{ __schema { mutationType { fields { name } } } }"}'
```

Table/view create/update/delete mutations are currently disabled on the PostGraphile server, not by smart tags in the DB.

Reads are public too: every column of every `production` table/view is world-readable, so **never expose admin/auth identity** (researcher emails, etc.). Tag such columns, or whole admin-only tables, with `@omit` the same way (`COMMENT ON COLUMN ... IS E'@omit\n...'`). See `2026_09_23_5_omit_admin_identity_graphql.sql`.
